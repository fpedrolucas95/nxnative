# The Legend of Zelda: Ocarina of Time

The Switch 2 base dump reaches its title screen on the Mac. VideoToolbox decodes the 1920×1080 AV1 track. The movie library runs its NDVE compute shaders to produce the background behind the logo and menu. Gameplay validation is open.

## Profile

SDK 22.2.8, NVN API 231.40, with Nintendo's sead, agl and gsys. The three loaded modules are `main`, `subsdk0` (NintendoSDK_movie), and `sdk`. The NPDM declares 48 MiB of system resources. Startup requests a 6.20 GiB heap, which fits in the profile's 12 GiB reservation with the stack and alias regions. The registered build is the supplied base dump (`v0`).

## Recovered MacBook Air M4 settings

The November 5, 2026 v131072 session used the settings in [mac.env](mac.env).
They are runtime settings, separate from the host's general defaults and from
generated build files. Build with that file and use the supplied runner afterward:

```sh
# PYTHON is the shared tool venv's Python; NUP is the original package path.
"$PYTHON" scripts/build_ipa_from_nsp.py "$NUP" --platform mac \
  --env-file "$PWD/dm/games/0400486024DEC000/mac.env"
python3 scripts/play_oot.py "$(dirname "$NUP")/0400486024DEC000_build"
```

`play_oot.py --print-command <build folder>` shows the exact environment without
building or launching. It uses a sibling `0400486024DEC000_saves/save` when present
(the saves preserved during cleanup), otherwise the build's `run/save`. An explicit
`--save <folder>` overrides that choice. Saves are not overwritten or recloned.

| Setting | Recovered value | Evidence and limit |
|---|---|---|
| `DM_RENDER_SCALE` | `0.5` | Runs 16–19 logged `3D views rendered at 0.50`; the user reported improved frame rate. |
| `DM_UPSCALER` | `metalfx` | The logs identify the 22 NDSR shaders replaced by MetalFX. |
| `DM_NVN_ENC_THREAD` | `1` | The logs confirm the encode thread; its indirect-mesh abort was fixed before run 16. |
| `DM_NVN_POOL_HEAP` | `0` | The user reported that run 17 removed the fog/DOF blocks; run 18 with mode 2 retained them. This is a visual workaround. |
| `DM_NVN_RES_LIMIT_MB` | `11300` | The guard used in those runs. Run 17 reached 11,992 MB of residency and stopped; disabling heaps did not solve memory pressure. |
| `DM_OPMODE` | `1` | Docked, as in the later runs. The earlier handheld experiment was reported slower. |

The unsuccessful `DM_NVN_GMEM_RES=0` and `DM_NVN_TEX_MIP_SKIP=1` experiments are
not restored: the preset explicitly selects their normal defaults, 1 and 0.
The final HMMA optimizer correction and same-format heap restriction were saved
in source and translator chain `72458830f2f7`, but their shader rebuild was
interrupted before a completed gameplay test. The native-movie-renderer cut at
`main+0x3b5f51c` was proposed, deliberately not applied, and remains unapplied.
Missing textures, foliage speed, DOF aliasing and heavy-scene GPU cost remain open;
this preset does not establish a fully correct or stable configuration.

Build outputs, the compiled shader image and pipeline caches were removed during
cleanup. The source corrections, runtime preset and saves survive; a playable
installation requires rebuilding those generated files from the NUP.

## Mac dry run

Use the rewritten `patched_v0` and the original extracted `base/romfs`. Build the host with `make -C dm/host GAME=0400486024DEC000` and use the [Mac shader build](../../../docs/development.md#build-by-hand-mac). From the repository, set `DUMP` to the folder containing `base` and `WORK` to the build and run workspace beside it.

```sh
mkdir -p "$WORK/run/save" "$WORK/run/temp" "$WORK/font"
python3 dm/tools/make_ext_font.py "$WORK/font/nintendo_ext.ttf"
DM_ROOT="$WORK" DM_ROMFS="$DUMP/base/romfs" DM_SAVE="$WORK/run/save" \
  DM_TEMP="$WORK/run/temp" DM_MSL_DIR="$WORK/shader/cache" DM_FONT_DIR="$WORK/font" \
  DM_NVN_SHMAP="$PWD/dm/games/0400486024DEC000/shader_map.tsv" \
  DM_WINDOW=1 DM_METAL_HUD=1 DM_FOCUS_KEEP=1 DM_AUDIO=1 \
  dm/host/dmhost "$WORK/patched_v0"
```

`DM_FOCUS_KEEP=1` lets the title keep playing while another app has focus. The profile prewarms the 11 NDVE compute pipelines used by the title. On the Apple M5 that took 17.7 s on a cold run, with a progress screen, and 7 ms with the archive warm. Compiling the same pipelines during the first submission had blocked the first movie frame for tens of seconds. The larger scene shader set also triggers a separate graphics-pipeline prebuild. On the first run with that set, the startup screen took 86.9 s to hand out all pairs, and the remaining workers finished after 110.6 s total.

Start a new game to reproduce the opening scene transition. With the test save and title flow, `DM_KEYS=f2600:A,f2950:A` advances the menu automatically. `DM_NVN_SHDUMP` saves control sections and code for missing keys to the directory it names.

For a run past the opening, copy the committed save folder to the new run's `DM_SAVE` and load slot 00 from the menu. The checkpoint contains both `slot_00/progress.sav` and `slot_00/caption.sav`. The load screen identifies it as **Kokiri Forest Autosave**. A windowed reload reached the playable scene with the HUD and controls, so rendering can be tested without replaying the movie.

## Found on this game

- The online library's [eventfd for its poller](../../../docs/reference/services.md#eventfds-served-offline) and the [virtual audio input list](../../../docs/reference/audio.md#no-virtual-audio-input-devices-sdk-22) blocked startup.
- The SDK's [NDVE pack](../../../docs/reference/shaders.md#the-movie-librarys-ndve-shader-pack) contains 22 compute programs. The title route uses 11.
- The [raw write log and pool lookup](../../../docs/reference/frame-rate.md#a-full-frame-shader-overflows-the-raw-write-log) took the windowed title movie from a 47.6 ms median to 16.67 ms on an Apple M5, at 1920×1080 decode. A steady 300-frame window averaged 60.0 fps and its GPU median was 15.94 ms. A simultaneous ten-worker shader build caused additional stalls. The same run returned to 60.0 fps when the build paused.
- A [play report send](../../../docs/reference/services.md#an-asynchronous-play-report-opens-prepou) aborted at the first gameplay transition after a failed `prepo:u` connection. A Mac dry run with the offline completion finished the 9,254-picture opening movie and continued submitting the live scene. The title-only shader set left the scene black.
- The white 3D scene was agl's [conditional depth clears](../../../docs/reference/rendering.md#conditional-rendering-evaluated-at-replay) run unconditionally (resolved; the profile sets `render_cond on`). The main opaque pass tests `EQUAL` against a copy of the prepass depth that agl clears under a condition right after copying, a clear the console skips. Without the key the copy was 1.0, no lit geometry passed, and the full-screen sky (`943d8c0ece545cc8`) showed through. With the key the saved Kokiri Forest scene renders: Link, the ground, the props, lighting and the HUD.
- Mesh-shaded models were missing, among them the door of Link's house: the split read six stage slots of each BNSH program, and NVN2 keeps [task and mesh shaders in slots 7 and 8](../../../docs/reference/shaders.md#task-and-mesh-shaders-in-nvn2-bnsh-program-slots-7-and-8) (resolved). The new split adds 491 mesh and 17 task shaders to the map, 53 of the 54 keys the Kokiri Forest scene had asked for. 511 of their 520 build; the door renders.
- Kokiri Forest ran at about 20 fps with the GPU two-thirds idle: the [bindless pool table was rebuilt for every registration](../../../docs/reference/frame-rate.md#a-bindless-pool-table-rebuilt-for-every-registration), and about 12,000 descriptors of finalized texture objects churned the ghost ring (resolved). The frame is now 16–21 ms at the median on an Apple M5, submit 5–8 ms, and the GPU (14–21 ms) is the limit.
- The first 3D scene exhausted Metal memory when [bindless pool walks churned finalized textures](../../../docs/reference/nvn-objects.md#a-bindless-pool-churns-finalized-textures-within-a-submission). On the Apple M5, the failing run reached 18,930 MiB of residency. With submission-local backing, residency was 7,946 MiB about ten seconds after the movie and 7,871 MiB at 35 seconds. The opening 3D scene and its subtitles presented, and the test host exited normally.
- Loading the Link's house autosave hung the GPU in six of nine runs, with any upscaler: [more memory pools than the raw pool table had entries](../../../docs/reference/shaders.md#more-memory-pools-than-the-raw-pool-table-had-entries). The load made 4,097 to 4,522 pools. agl's task shaders `99280b7b8aae78df` and `47f9b38490dcf9a2` then read 0 for a range's ends and looped 2<sup>27</sup> times. Upstream issue #1265 saw the table pass 4,095 about eight minutes into gameplay, with floors missing. The table now grows with the pools; the November 5 M4 runs reached 4,545 pools and continued to frame 7,800 with the fix.
- Compute shaders `1f78730053feb036` and `e172bd7ec218ab8e` nested 259 brackets, past the Metal front end's 256, and were left out: [bracket nesting past the front end's 256](../../../docs/reference/shaders.md#bracket-nesting-past-the-front-ends-256) (resolved; both compile).
- On v131072 Kokiri Forest's ground had no texture, the foliage twitched and bright areas were burnt out (MacBook Air M4, 16 GB). 34 shaders lost their [float atomic adds](../../../docs/reference/shaders.md#float-atomic-adds-dropped-f32ftzrn) in translation: 8 `TerrainGround` and 13 `Foliage` pixel shaders, and 13 agl `AglShader` programs. The adds translate on chain c0259cb667e3; the November 5 capture showed the path and grass textured afterward. Exposure, other missing textures and foliage motion remained open.
- The GPU ran out of an M4's 12 GB working set loading Kokiri Forest: one 305 MB virtual pool of transient render targets held 1,923 MB in 662 Metal textures, among them 85 depth textures at one offset (1306x1306 to 1920x1920). They can share [a placement heap per pool](../../../docs/reference/nvn-objects.md#textures-over-shared-storage-in-a-pools-placement-heap), one format at a time: with any format sharing, the depth of field's tile maps read other targets' bytes and the background blur showed blocks. Placement-heap sharing stays off by default (`DM_NVN_POOL_HEAP=0`); `1` and diagnostic mode `2` remain available for investigation. The exact DOF corruption mechanism and validation of the same-format restriction remain open.
- `DM_NVN_ENC_THREAD=1` stopped at the first [indirect mesh draw](../../../docs/reference/rendering.md#indirect-mesh-draws-on-the-encode-thread) (resolved). The profile now sets `enc_thread on`, so Mac builds encode on their own thread without the preset; the preset's `DM_NVN_ENC_THREAD=1` stays as the same switch by hand.
- The NDVE and NDSR networks' HMMA read undefined fragments after [dead-code removal followed a producer with outputs still read](../../../docs/reference/shaders.md#dead-code-removal-following-a-producer-with-outputs-still-read) (chain 72458830f2f7; not yet checked in the game).
- Render scale: `patches.py` returns the host's `DM_RENDER_SCALE` (0.5 to 1.0 of the output; 1.0 keeps the game's dynamic resolution) where the dynamic-resolution controller returns its level's scale (main+0x805ff0, found by lunks). 0.5 renders 1024x576 into the 2048x1152 frame.

## Open

- The foliage moves at about twice the speed of the character (reported on v131072 with and without the heap fix; cause unknown).
- Some ground textures still do not load after the float atomic fix (resolved). Measured again on the chain `72458830f2f7` Mac build of 5 November (preset, save slot 00, `enc_thread on` from the profile): shots at frames 1400 and 3200 show the Kokiri pond's surface as flat backdrop blue with the foliage and grass over it drawn, while the path stones and grass around it are textured. The cause was the terrain height tiles, not a texture the encode missed: the ten 260x260 R32F height tiles are CPU-written with no flush in a 202 MB pool (flags 0x24) that also holds GPU-written textures, so `tex_cpu_content` refused all of them, every terrain patch lay flat far below the player and the sky (or the backdrop) showed wherever only the terrain covers the ground. GPU-written storage is now tracked as ranges (upstream PR #1390): on the same build and route the log takes the height tiles from their storage (`texture written by the CPU before its first use … 260x260x1 format 0xa (uncompressed, storage the GPU has not written) pool flags 0x24: uploaded from its storage`) and the frame-1600 shot shows the pond's water surface and banks where the flat blue was. It is not a binding the encode misses: the saved pass dumps (frames 3000 and 4761, the Saria scene) show no `dummy` texture binding at all, and the `TerrainGround` draws (`5ccdd001a21f5594` / `c85555a82fd0d009`) sample one per-chunk texture directly (IDs 6874/6873, serials 11679/11678 at frame 3000) with a 260x260 R32Float heightmap in the vertex stage; the bindless pool table is used only by `Model` passes, and the binary holds no virtual-texture, sparse or texture-feedback system for the terrain (sead's `TeraTerrain` BFRES, `TerrainTextureIndex`). So the texture is found and sampled; its content is what is missing, the same class as the fixed float atomic case. The upload counters leave a suspect: 5,545 first uploads against 31-60 re-uploads and 5,199-6,426 checks that found only writes beside a texture, with the tracker's own missed count at 0. Next probe on a playable build, on a chunk that lacks its texture: `DM_NVN_PASSDUMP_ALL=1` (the saved dumps print `K`/`B` only for a pass's first draw, so IDs 6874/6873 never got a `B` line), `texraw` of that chunk's serial against a good neighbour's, and `DM_NVN_DIRTYCHECK=1` to tell a missed re-upload from a GPU pass that never produced the content.

- On a MacBook Air M4 (16 GB, v131072, chain c7de80c08992), Kokiri Forest's frames took 42–55 ms on the GPU at the median (about 20–25 fps on screen), with a 9.8 GB footprint and no headroom to the system memory limit. Not measured again since the float atomic fix.
- CPU and RAM in Kokiri Forest (saved v131072 logs, MacBook Air M4; identification, no fix applied beyond `enc_thread on` above). RAM is the load, CPU follows it: before the scene loads the host holds 4.5 GB resident (2,601 residency allocations, 5.9 GB); loading Kokiri takes it to 10.3–10.5 GB resident, 9.9 GB GPU allocated, 10,409 allocations and 9.8 GB in the residency set, about 7,300 serial objects, with residency commits of 563–867 ms across the loading window and, in the worst saved window, submit+present at a 195 ms median (frame 250 ms). Measured fresh on the 5 November chain `72458830f2f7` build (preset): resident 11,663 MB and 12,375 residency objects at frame 2700, then the guard stopped the run at 11,309 MB of residency set (`[RED] residency set 11309 MB passed DM_NVN_RES_LIMIT_MB=11300: stopping the game`; 8,109 textures / 5,530 MB and 4,615 shared buffers / 5,878 MB in the set), with texture views made at volume alongside (95,884 views made for 6,276 textures in the frame-3000 window) and 859 of 1,749 shared textures unreferenced. In the steady scene the guest takes about two cores (main thread plus `ModuleSystemWorker` threads, yields in short runs under the 2 ms back-off, so real handoffs, not idle spins), the host's own submit is 0.23–0.25 ms a frame, and the GPU (about 65 ms median in the heavy saved windows at render scale 0.5, attachments about 330 MB a frame) is the limit; new-area pipeline compiles add spikes (one saved window: 234 ms of predictions and about 2 s of base compiles). Measured on the playable chain `72458830f2f7` build (5 November, same save and route, frames 1500–1800 windows, the guard lifted for the runs): the preset alone took frame p50 69.9 ms / GPU p50 85.3 ms at 11.77 GB resident; `DM_NVN_TBDR=1` took 26.6 / 35.1 ms at 12.25 GB with the frame-1600 picture checked (foliage and terrain as before, the pond surface missing either way), and the preset now sets it. `DM_NVN_GMEM_RES=0` shrank the residency set (8,408 objects against 11,815; GPU allocated 10.31 against 11.20 GB) but blew the exposure out (frame-1600 shot washed white) and did not lower the resident footprint (11.86 GB): rejected, and it explains why the preset pins `DM_NVN_GMEM_RES=1`. `DM_NVN_TEX_MIP_SKIP=1` measured smaller (frame 41.7 / GPU 67.8 ms, resident 11.30 GB, picture checked) and stays off; combining it with TBDR is unmeasured. Still open: placement-heap sharing past one format (the depth-of-field corruption above) and a smoke/bench route for this profile (it has none, so `regress.py` covers its chain only).

- Of the task and mesh shaders, nine do not translate: eight foliage shaders stop at Ampere opcode `0x243` (packed conversion, source A `RZ`, mode `0x0000c4ff`; three of them, `604134a5262ff670`, `ecead5cd0569091f` and `fed302d791a4ba43`, are drawn in Kokiri Forest), and one at ISBERD mode `0xb8` in a task or mesh shader. The scene also asks for `d17eefaff4f0bc23`, whose code is in none of the shader archives.
- The title-only build logged 3,331 distinct mapped libraries it could not open, including 363 shaders that failed when setting up programs. A targeted build for those programs and their dependencies translated 6,132 of 6,134 shaders. The two failures are foliage compute shaders `8692b34b521225be` and `83df46a0b1b379b4`, both with Ampere opcode `0x243`.
- With `render_cond` on and the shader build still incomplete, Kokiri Forest showed a hard horizontal cut, sky colour above the horizon over the trees. The volumetric fog composite (`888c1068ac8f7043`, agl) takes a pixel whose R32Float depth copy reads above 0.9999 as sky and paints the sky lookup there. The pass that fills that copy draws with agl's full-screen vertex shader `fb1ed54be1baced1`, which that build had not reached yet, so the host skipped the draw (`draw skipped: no render pipeline`) and dropped the target's store. Retest with the stamped full build. The sky lookup's peaks (about 105, 67 and 36 in RGB) are unverified against the console.
- The opening scene calls `nvnCommandBufferDrawMeshTasksIndirect`, which the host does not implement. On `v0` the probe caught the return at `main+0x2be2dc0`; the branch builds the command buffer pointer in `x0` and the indirect argument address in `x1`. It does not set `x2` on that path. A separate sample of the first 64 bytes at the indirect address returned zeros after the call; the populated record's layout is still unverified. The title-only run logged 11 keys missing from the map. The expanded run captured seven of them before the memory failure. A byte-for-byte comparison found none of those seven code areas in the extracted shader package.
- The 3D scene's CPU cost (37–59 ms a frame, with pool walks of about 33,000 descriptors) is [resolved](../../../docs/reference/frame-rate.md#a-bindless-pool-table-rebuilt-for-every-registration). Open: the GPU's 14–21 ms a frame in Kokiri Forest, which still drops frames below 60 fps; TBDR optimizations are off for this bindless game (`DM_NVN_TBDR=1` turns them on), and attachments load and store about 330 MB a frame.
- The Nov. 4 Lichii branches offer two shader leads. Its [packed conversion lowering](https://github.com/zortos293/Lichii/commit/35c043b3efaa147d1c1afe8a52cdf19fa92b77bf) handles opcode `0x243` with source A set to `RZ` and mode `0x0000c4ff`; both of this game's failed foliage programs use two registers and mode `0x000004ff`, which needs independent verification. Its [floating-point global reduction](https://github.com/zortos293/Lichii/commit/3aa89d1cdbe58a2bd5ded06b9c615c78da2ade70) matches a separate `F32FtzRn` diagnostic in the Mac shader build, where the translator drops that operation. Neither of the two shaders in the sky lookup and draw uses those instructions or the gather opcodes from Lichii's [fog work](https://github.com/zortos293/Lichii/commit/375c4a472bd95fdfaae0de6e3f192499cd14f806).
